# Repository repair owner contract v1

This source contract is disabled until explicitly composed. It adds no release,
provider deployment, implicit feedback approval or acceptance authority. The
installed mutable profile, current repository resolver, actual Workspace reader
and trusted repair policy must all exist. `max_repairs` in the AgentOps delivery
consumer remains zero until its consumer continuation slice is implemented.

The new owner operation is `POST /api/repository-runs/v1/repairs`, authenticated
as the existing caller and bound to a protected `RepositoryRepairService`. Its
TypeSpec is `contracts/repository-repair-v1/main.tsp`; the integrity-pinned Python
SDK and schemas under `sovite/repository_repair_contract` are generated by
Vuoro's existing contract generator. The request selects the parent, exact
candidate and feedback release, and a
lowerable `max_cost_usd`; it accepts no portable packet or alternate goal/base.
The owner reconstructs the original portable-work intent from its authenticated
parent record and reuses `validate_run_packet` and current binding admission.
Goal, repository, executor, canonical base, deadline and concurrency remain the
parent's exact values. No competing portable-work model is introduced.

The principal-bound preview is SHA256 of canonical JSON with `principal` and
`repair` containing `parent_run_id`, `candidate_sha256`, `feedback_release_id`
and `max_cost_usd`. The caller persists this complete request and its
idempotency key before sending. A lost acknowledgement replays that same intent.
A changed credential cannot reuse the preview as a different principal.

The parent must be a completed run owned by this same caller and workspace,
with exactly one matching retained-candidate receipt in its actual owner
history. The configured `CandidateRetention` reads the exact ready version
through released Workspace APIs, after checking current class and destination;
Workspace supplies current membership. Caller-supplied class labels grant no
read. That read does not grant permission to send the candidate to a model.
Before the owner stores child input, it separately rechecks the exact candidate
receipt's existing output release: same parent source, exact content digest,
current output class within the child's input ceiling, and the child's selected
model destination in the release. This check repeats in admission, before and
after seeding, and in ongoing lease/model-use authorization. A storage-only
release or a subsequently revoked approving identity stops the child even when
feedback remains eligible. The immutable parent candidate is preserved independently of the child's
workspace. An admitted input copy is not a live Workspace capability: this slice
does not install a membership-revocation watcher that retroactively destroys
copied bytes or cancels an admitted child. Every later Workspace read must
recheck current reader authority; ongoing native calls independently recheck
current Sovite grant/binding and both candidate and feedback release chains.
Admission and execution recheck the original base, allowed areas,
current grant, generation, executor publication and qualification.

Feedback uses an existing output release under an explicitly configured contract
whose review procedure permits trusted check/review feedback about that exact
parent candidate. Commissioning must establish that procedure; a model output
or agent-written claim is not a trusted check result. This source neither
creates that contract nor approves feedback. Its released content must match
`RepairFeedback` from the TypeSpec: exact parent run, candidate export digest
and tip, failed check or review, and bounded feedback text. The existing output
owner rechecks the source job, current approving identity, exact bytes, contract
revision, class and model destination before any feedback enters the native
process. Revocation of that release or source chain stops further execution.
The source job is the parent candidate; the checking operation is named by the
existing release's evidence references, never fabricated as a parent model act.

The trusted host supplies `RepairPolicy` with at most three repairs and an
explicit list of feedback contract IDs. Inside the existing `Platform.submit`
authority transaction, admission reads the completed lineage and refuses a
second logical successor to the same parent. It accounts for the original
run and every repair's settled usage, and caps the child's maximum spend by the
root's remaining budget. Any pending reservation, active slot or uncertain
ancestor refuses new paid work. A declined or unacknowledged operation never
refunds unknown exposure. Idempotent replay returns the same child; it creates
no extra job. These observations remain in existing Job metadata and private
artifact storage, with no parallel work or authority ledger and no schema DDL. Existing run
evidence retains a `repair-predecessor` locator and exact seed digest after
candidate capture, so fresh readers can traverse the bounded owner lineage.

Before native execution, the owner imports the exact retained bundle into the
new attempt workspace. It verifies export, receipt, bundle and patch hashes,
canonical-base ancestry, bounded linear history, allowed areas and regular file
modes. The original goal remains unchanged. Only an executor explicitly
supporting `repair_context` can receive the separate keyword record with root
and parent run IDs, repair number, candidate tip, and currently approved feedback
and its digest. The native runtime retains its loop, commands and model choice.
A missing driver, stale binding, unknown outcome or invalid input stops rather
than falling back to an unrecorded new run.

The actual owner tests use the shared Worker, real Git, output approvals and
released Workspace HTTP APIs backed by PostgreSQL. The callback is deterministic
test code and supplies no native execution or service qualification. PostgreSQL
successor races use separate Platform transactions and a deterministic start
barrier. Set both `SOVITE_WORKSPACE_TEST_DSN` and `SOVITE_TEST_POSTGRES_URL` to
explicit disposable UTF-8 databases to run all repair cases without skips.

## Feedback-context read and protected composition (contract1.1)

`POST /api/repository-runs/v1/repair-feedback-context` accepts only
`parent_run_id` and `feedback_contract_id`. The caller must own the completed
parent and be an enabled approver under that exact current installed feedback
contract, which must also belong to the protected repair policy. The source,
class, model destination, qualification and candidate release remain current.
The reply supplies the exact source digest, contract revision, generation and
candidate selectors needed by the existing `POST /api/output-releases` API.
This read creates no approval or job and exposes no original task, candidate
bytes, feedback text, credential or effect capability.

A qualified protected consumer can use its existing caller credential to approve
its trusted check feedback only when that machine procedure is actually enabled
by the output owner. The existing approval operation remains the authority and
rechecks the supplied source, revision and generation. An ineligible consumer
preserves an actionable stop; a real release may be supplied by another
already-authorized procedure. This adds no mandatory human step or new approval
writer. Before retrying an unknown approval, a consumer must reacquire the same
owned eligible context so a changed credential cannot silently replay as a
different approving principal. Exact repeated approval bytes converge through
the existing content-addressed release operation; the repair request keeps its
own persisted idempotency key. Tests drop each actual HTTP acknowledgement after
its owner commits and assert one added release and one child.

The private `sovite-repository-runtime/v1` installation may add
`repair: {max_repairs: 1, feedback_contract_ids: ["qualified-feedback"]}`.
Absence or null keeps repair disabled. Enabling requires the same configured
retention/current-reader service and a driver explicitly supporting
`repair_context`. A malformed requested policy, absent retained reader or
unsupported driver disables the optional repository runtime, rather than
silently running a workflow without its requested repair support. This
composition does not install an output contract, qualify a native driver, or
prove a live service. Upgrade/rollback must preserve in-flight journals and
reconcile unknown outcomes before changing the protected installation.
