# Resource-owner pod gateway source slice

Status: uninstalled source; no deployment, customer qualification, high availability or live-cluster evidence. Work-owner basis and acceptance remain separate: execution currentness does not establish work acceptance, and this slice does not integrate Sprintctl.

The resource gateway runs independently and polls a fixed HTTPS execution-owner origin using a separately enrolled expiring gateway credential. The authenticated outbound channel conveys proposals, not resource permission. Execution owner enrollment binds gateway identity and audience to tenant, workspace and domain; workload admission is tied to the current started execution lease. Gateway policy is resource-owner controlled through a separate admin app, disabled without its separate credential, and binds the principal and exact catalog target. Routine access has no admin route. No worker supplies a target URL, path, namespace or resource credential.

A commissioned resource-owner policy explicitly classifies the fixed named-pod projection for its C1 or C2 source class, C1 output class and destination; C3 sources are refused in this profile; C3 source/output and private-destination workflows are unsupported and unqualified here, not prohibited by the architecture; it is not a general classification of pod data. The fixed projection contains workspace/domain/observation identifiers, namespace, name and a closed phase vocabulary. Owners must decide whether those identifiers and phase are appropriate for the destination. Raw Kubernetes output and arbitrary summaries never enter this release. The execution owner independently applies its installed output and reader policy before invocation and disclosure, including the actual job input class, current execution grant and model and execution destination clearances. A C0 job cannot be upgraded by this grant. No policy is installed by default.

The gateway requires an owner-only state directory and private regular database file; installation creates the file with mode 0600 and refuses symlinks or broader access. The owner binds a retained result to the gateway enrollment that delivered it and rechecks that enrollment and exact current scope before reader disclosure. Credential fingerprints are rechecked under the owner lock; result authorization is decided by a fresh currentness check immediately before the stored-result decision. Later transport timing does not extend that authorization. The gateway records the operation ID and canonical request digest before the single target read. A changed request conflicts; an admitted operation without a retained observation after restart is UNKNOWN, never automatically read again. It records immutable bounded bytes, digest and release outcome, including policy revision, destination and actor, before delivery. A retry can deliver only retained bytes after fresh owner currentness, resource policy and exact output checks. The local SQLite history is resource-owned operational state, not a work, execution, authority or publication ledger. Local locking provides no distributed replica fencing or exactly-once guarantee.

Installation is explicit: `sovite-resource-gateway --database PATH install`. Admin and polling are distinct process modes. Admin binds loopback and requires `SOVITE_RESOURCE_ADMIN_TOKEN`; production must provide an appropriately isolated private administration path. Polling requires a fixed HTTPS origin, CA and gateway credential through `SOVITE_RESOURCE_OWNER_ORIGIN`, `SOVITE_RESOURCE_OWNER_CA` and `SOVITE_RESOURCE_GATEWAY_TOKEN`. These source settings are not evidence of a commissioned deployment. The gateway's local database must be protected and backed up according to the resource owner's operational policy.

Execution-owner schema v6 is an explicit offline migration. Run `sovite db migrate` with the configured migration role before starting the API or workers; startup checks compatibility and does not execute DDL. This changes earlier `startup` behavior for fresh and older databases: they now refuse until migrated. Production installation, credentials, scheduling and rollout remain outside this source slice.

The polling process emits structured fixed-code diagnostics to stderr. Missing or invalid local policy, an unavailable store and invalid owner configuration fail startup with distinct codes. Poll failures and unknown, unavailable or refused operations are counted in `poll_degraded` records, emitted immediately and at most once per minute thereafter while failures accumulate. Records contain counts only, never exception text, credentials, target output or identity fields. The polling interval remains five seconds; an incomplete admission remains UNKNOWN and is not automatically read again.
